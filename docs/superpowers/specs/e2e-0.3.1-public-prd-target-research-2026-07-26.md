## 第一方来源与固定基线

### PRD

TodoMVC 固定 `app-spec.md` 是应用行为规格。其[功能要求原文](https://github.com/tastejs/todomvc/blob/ff43b02e59dfa604386bb382034b2cd07c2bcd8a/app-spec.md#L80-L122)定义了：

1. 空列表时隐藏主区域与页脚；
2. 输入标题并按 Enter 新增，trim 空标题不创建，提交后清空输入；
3. 单项完成、全选及取消全选；
4. 双击进入编辑，Enter 或 blur 保存，Escape 放弃，空标题删除；
5. 剩余数量与 `item/items` 单复数；
6. hover 后显示删除按钮并删除单项；
7. Clear completed 的出现、执行和隐藏；
8. localStorage 持久化，数据字段与存储 key 格式；
9. All、Active、Completed 路由、过滤状态和 reload 后路由保持。

固定 PRD 原文：<https://raw.githubusercontent.com/tastejs/todomvc/ff43b02e59dfa604386bb382034b2cd07c2bcd8a/app-spec.md>。

## 写入、Cleanup 与风险边界

### 数据与网络边界

固定实现的 todo 数据流是：`TodoModel` 初始化时通过 `localStorage.getItem` 读取，模型变化后通过 `localStorage.setItem` 写回。对应用自有源码的核验未发现 `fetch`、`XMLHttpRequest`、`sendBeacon`、WebSocket 或 `window.open`。

因此：

- 新增、编辑、完成、删除和清理只改变隔离 Profile 中当前 origin 的 localStorage 和 DOM；
- hash 路由只改变当前 document 的 fragment 与本地渲染；
- 应用不产生 POST、PUT、PATCH、DELETE 等业务 HTTP 请求；
- 不涉及账号、Cookie 身份、共享数据或跨用户数据；
- reload 可验证持久化，UI 清空后再次 reload 可验证 cleanup；
- 一次性 Profile 销毁是最终兜底，不污染日常 Chrome 数据。

### Cleanup 顺序

正式运行采用以下固定策略，不把决策留给执行者：

1. 在全新一次性 Profile 打开目标，确认初始列表为空；
2. 只创建带本次 `runId` 的 todo；
3. 功能和 Persistence 验收完成后回到 All；
4. 通过 UI 将所有残留项目标记完成并执行 Clear completed；
5. reload 后确认列表为空，`react-todos` 中不存在本次 `runId`；
6. 关闭页面并销毁一次性 Profile，保存 cleanup receipt。

若 UI cleanup 失败，运行结论必须是 `cleanup-failed`，不得发布 accepted；随后仍销毁 Profile 以避免本地残留，但 Profile 销毁不能掩盖 UI cleanup 失败。

### Gateway 最小权限

TodoMVC 场景只允许 `https://todomvc.com/examples/typescript-react/` 页面及必要同源静态资源的 GET/HEAD。拒绝：

- 非批准 origin；
- POST、PUT、PATCH、DELETE 等 HTTP 方法；
- 页脚站外链接导航；
- 页面脚本发起的非预期网络请求。

浏览器 localStorage 变化是可清理的 `browser-local-write`，不得伪造 Gateway forwarded write、lease 或 HTTP cleanup receipt。

### 外部目标风险

- 官方站点可能不可用或部署新版本；状态码或摘要变化应判为环境/来源漂移，不能误报为产品失败。
- 公开目标不受本仓库控制，不得注入脚本或修改业务 DOM 来使测试通过；如仅补充测试身份标记，适配器和摘要必须进入报告且不得改变业务行为。
- 存储 key `react-todos` 不符合 PRD 的 `todos-[framework]` 命名格式。该差异不妨碍 Persistence 功能验收，但必须作为 Requirement 级偏差发布，不能忽略。

## 被否决的主目标：现代 React 示例

官方现代 React 页面 <https://todomvc.com/examples/react/dist/> 同样无需账号，且线上 `index.html`、`app.bundle.js` 与固定提交一致。但其 [`app.jsx`](https://github.com/tastejs/todomvc/blob/ff43b02e59dfa604386bb382034b2cd07c2bcd8a/examples/react/src/todo/app.jsx) 使用 `useReducer(todoReducer, [])`，没有 localStorage；[`input.jsx`](https://github.com/tastejs/todomvc/blob/ff43b02e59dfa604386bb382034b2cd07c2bcd8a/examples/react/src/todo/components/input.jsx) 没有 Escape 分支；[`footer.jsx`](https://github.com/tastejs/todomvc/blob/ff43b02e59dfa604386bb382034b2cd07c2bcd8a/examples/react/src/todo/components/footer.jsx) 输出额外感叹号。

它可以用于验证 Runtime 能否发现三个真实产品偏差，但不适合作为本次希望覆盖 Persistence、Escape 和正确计数的主验收目标，因此降级为可选负向用例。

## 不能由 TodoMVC 单独证明的 Runtime 能力

TodoMVC 是单页面、纯前端 localStorage 应用，天然没有：

- Popup；
- 多页面/多 Tab 协同；
- 带 JSON Body 的 POST/PUT/PATCH/DELETE；
- 服务端写入后的独立 cleanup session；
- 服务端事务、鉴权和共享数据隔离。

0.3.1 最终能力结论必须合并两组证据：

1. **公开 TodoMVC PRD 验收**：证明公开 PRD 摄取、语义确认、真实页面多动作执行、localStorage Persistence、browser-local cleanup、报告与资产追踪；
2. **受控 full-playwright Golden fixture**：证明 Popup、多页面、JSON Body 写入、Gateway forwarding、cleanup session 和 cleanup 后 reload。

只有两组都完成，才可以声称“0.3.1 的 PRD 驱动 E2E 全链路与完整 Playwright 能力均已验证”。

## 最终建议

正式执行使用上述固定 PRD、固定提交和 TypeScript+React 官方 URL，不再重新选择目标。执行前重新计算 `index.html` 与 `js/bundle.js` Git blob 摘要；一致后依次执行 TC-01 至 TC-10。最终报告必须把“Runtime 链路是否完整”和“目标产品是否完全符合 PRD”分成两个 verdict：前者应覆盖计划动作、cleanup、证据和追踪是否完整；后者应如实记录 `react-todos` 命名偏差。Popup、多页面和 JSON Body 写请求继续引用本仓库 0.3.1 full-playwright Golden 的独立通过证据。
