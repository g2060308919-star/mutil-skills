1. 校验工作区干净，且本地与远端 `v0.6.0` 均精确指向当前发布提交。
2. 清理并重新构建全部 TypeScript workspace。

4. 在全新临时 HOME 与空白用户项目中，从公共 Registry 精确安装 14 个 `0.6.0` 包。
5. 校验 Registry tarball、lockfile integrity、包版本和内部依赖版本。
6. 安装 Runtime，并移除用户项目中的安装输入，证明运行不依赖仓库源码路径。
7. 执行 Runtime doctor，验证系统 Chrome、Gateway 和正式 RPC 环境。
8. 运行 PRD 语义、测试设计、浏览器执行、证据、cleanup、Reload 和最终报告链路。
9. 要求测试结果零失败、发布 Golden 零跳过，并清理 Runtime 自有临时目录。

## 0.6.0 新增能力的验证范围

0.6.0 新增的 stable Runtime 更新能力已由全量单元、集成与安全回归测试覆盖，包括：

- 基于官方 `tuf-js` 的 root、timestamp、snapshot、targets 信任链；

- HTTPS origin、redirect、target URL、长度、SHA-512 与 npm integrity 绑定；
- 下载文件的当前用户、单硬链接和 `0600` 权限检查；
- candidate closure 安装后依次执行 doctor 与 canary，成功后才切换 new-run default/LKG；
- 已存在 Run 保持 digest 绑定，更新只作用于新 Run；
- crash-recoverable 更新锁与可审计激活记录；
- `latest` 继续 fail-closed，`offline` 与 `pinned` 保持兼容。

## 明确边界

- Registry Golden 验证的是已发布 0.6.0 的安装和 E2E 执行闭环，不等同于已经启用一个真实生产 stable 元数据源。
- 生产 stable 更新源仍要求真实的 2-of-3 离线 root/targets 密钥、经审查的 bootstrap `root.json`、受控 HTTPS metadata origin、密钥轮换与撤销演练，以及 Node 22/24 和目标操作系统的 Registry Golden。仓库没有使用测试密钥伪造这些生产条件。
- 在上述生产条件完成前，stable 网络更新会明确拒绝，而不是降级为不验签更新；用户仍可使用已发布的 `offline` 或显式 `pinned` Runtime。
- 本次真实浏览器为系统 Google Chrome，不据此宣称 Firefox 或 WebKit 已完成同等级真实验收。
- 任意业务 PRD 是否能 100% 自动判定仍取决于业务 Oracle 与测试数据可用性；无法自动化的义务必须显式标记为人工或 N/A，而不能静默遗漏。
