# 测试驱动开发

TDD 是 red -> green 循环。这个 skill 用来确保循环产出的测试值得保留：什么是好测试、测试应该写在哪里、哪些是反模式，以及循环规则是什么。每一轮循环都适用这些内容，应在循环前和循环中查阅，而不是事后补看。

探索代码库时，如果目标项目中存在 `CONTEXT.md`，先阅读它，让测试名称和接口词汇与项目领域语言保持一致，并遵守你正在触碰区域的 ADR。不要假设本 skill 包自身携带目标项目的 `CONTEXT.md`。

## Mutil Skills 独立安装测试基建预检

当这个 skill 作为独立 Agent Skill 包安装，且 host runtime 没有自动解释 `skill.manifest.json` 时，在正常 TDD 流程前执行以下预检：

1. 检查 `package.json` scripts、依赖、lockfile、测试配置文件，以及可识别的测试目录。
2. 如果已经存在完整的 Jest 或 Vitest 基建，复用现有测试命令。
3. 如果存在不完整的 Jest 基建，展示缺失的 Jest scripts、依赖、配置或测试结构，并在只补齐这些缺口前询问用户。不要把 Jest 项目迁移到 Vitest。
4. 如果没有测试基建，展示将安装 `@mutil-skills/foundation`、新增测试 scripts、创建样例测试的计划；默认 Vitest 环境由 `@mutil-skills/foundation/testing` 提供，不在目标项目生成 `vitest.config.ts`。
5. 用户确认计划前，不要安装依赖或写入文件。
6. 如果用户拒绝，不要修改项目，并说明没有可运行的测试基建时无法继续 TDD。
7. 测试基建可用后，继续下面的 red-green-refactor 流程。

## 什么是好测试

测试应通过公共接口验证行为，而不是验证实现细节。代码可以完全重写，测试不应该因此失效。好测试读起来像规格说明，例如“用户可以用有效购物车结账”能明确说明系统具备什么能力；它不关心内部结构，因此能经受重构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## Seam：测试写在哪里

**seam** 是被测试的公共边界：你可以在这里观察行为，而不需要深入内部。测试应写在 seam 上，而不是面向内部实现。

**只测试预先确认过的 seam。** 写任何测试前，先写下要测试的 seam，并与用户确认。不要在未确认的 seam 上写测试。你不可能测试所有东西，提前确认 seam 能让测试精力落在关键路径和复杂逻辑上，而不是散落在每个边角场景里。

询问：“公共接口是什么，我们应该测试哪些 seam？”

## 反模式

- **耦合实现**：mock 内部协作者、测试私有方法，或通过旁路验证（例如不用接口而直接查数据库）。典型信号是：行为没变，但一重构测试就坏。
- **同义反复**：断言用和代码相同的方式重新计算期望值（例如 `expect(add(a, b)).toBe(a + b)`、手工按同样逻辑生成 snapshot、断言常量等于自身），这种测试天然会通过，永远无法与代码产生分歧。期望值必须来自独立事实来源：已知正确的字面量、推导过的样例或规格。
- **横向切片**：先写完所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是事物形状而非用户可见行为，测试对真实变化不敏感，并且在理解实现前就锁定了测试结构。改用**纵向切片**：一个测试 -> 一个实现 -> 重复。每个测试都是一颗 **tracer bullet**，会响应上一轮循环带来的认知。

## 循环规则

- **先 red 后 green。** 先写失败测试，再写刚好让它通过的代码。不要预判未来测试，也不要添加猜测性功能。
- **一次一个切片。** 每轮循环只处理一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 重构属于 review 阶段（见 `code-review` skill），不属于 red -> green 实现循环。
